# Realtime admission HMAC rotation

Status: dormant continuity contract only. It does not read secrets, call a
service, alter the admission database, wire a route, or open any production or
paid-service latch.

## Security model

`realtime-admission-hmac-keyring.ts` derives a bounded set of versioned opaque
user/session bindings from an already verified Supabase owner and owned
assessment session. Raw identifiers and decoded key bytes exist only during
derivation; the returned value contains only 64-character HMAC outputs and key
version labels.

The reviewed policy separates three roles:

- exactly one `activeVersion` is allowed to create new ledger rows;
- lower, explicitly accepted versions are lookup-only during an overlap window;
- one higher `standbyVersion` can be pre-staged for rolling deployment, but
  cannot write until a reviewed policy change makes it active.

The entire set is capped at three keys: active plus two previous versions, or
active plus one previous and one standby version.

The initial checked-in policy is `v1` only. Environment values cannot change
it. Key material is passed to the dormant function by a future server-only
secret-manager boundary; this module never reads environment variables or
credentials.

New secrets must be canonical unpadded base64url or lowercase hex, decode to
32-64 bytes, and pass a conservative byte-diversity check. A bounded
`legacy-utf8` compatibility mode exists only for `v1`, rejects surrounding
whitespace, and reproduces the original string-secret derivation so a migration
does not orphan existing opaque rows. Duplicate versions,
duplicate decoded secrets, unexpected keys, noncanonical ordering, unknown or
retired versions, cross-version opaque pairs, and non-active write attempts all
produce the same content-free fail-closed error. Encoding checks are only a
guardrail: operational keys must be generated by a cryptographically secure
256-bit secret-manager generator.

## Database migration invariants

The application layer must remain dormant until a disposable-database suite
proves all of these invariants:

1. Add a non-null `binding_key_version` beside each stored user/session pair.
   Backfill every existing row as `v1` in the same transaction, before any RPC
   accepts versioned candidates. A null or unrecognized version always fails.
2. Reserve, finalize, and cancel receive the bounded candidate set and compare
   `(binding_key_version, user_key, session_key)` as one tuple. They must never
   mix a user key from one version with a session key from another.
3. The atomic reservation transaction checks every accepted tuple for an
   existing session or idempotency record, then writes only the active tuple.
   Candidate probing must not expose which version matched.
4. Database constraints permit only the reviewed version allowlist. Changing
   the allowlist, active version, or minimum version is a reviewed migration;
   deployment flags and secret availability are not authority.
5. All application instances learn a standby key before it becomes active.
   Activation occurs only after fleet convergence is proven, so old instances
   cannot create a second reservation under an older opaque session key.
6. During overlap, finalize/cancel/reconciliation accept both the new active
   tuple and retained previous tuples. New reserve writes only the active tuple.
7. The policy version and database allowlist advance monotonically. Rollback
   may return code but must never lower `activeVersion` after a new version has
   written rows; emergency response closes admission instead.

## Retirement invariants

A previous key can be retired only after the latest of:

- the maximum reservation lease and seven-day late-finalization window;
- the full 90-day terminal/idempotency-detail retention window;
- reconciliation and archive verification for every day containing that key
  version;
- proof that no live row, retry token, maintenance backlog, or rollback target
  requires the old version.

Retirement is a single reviewed release: raise `minimumAcceptedVersion`, remove
the old material from the server secret boundary, remove it from the database
allowlist, and prove unknown/old versions fail without an OpenAI call. Secret
deletion from the manager happens only after the database and fleet are fully
converged; it is not part of this code slice.

## Required activation proof

Before any latch changes, add real multi-connection tests for mixed-version
reserve races, same-session uniqueness across versions, idempotent replay,
rolling fleet convergence, standby-to-active promotion, rollback after first
new-version write, late finalization across the overlap, retirement rejection,
malformed candidate arrays, RPC timeout, and zero provider calls on every
failure. Log only contract/policy versions and aggregate outcomes—never opaque
keys, raw identities, secret fingerprints, or key material.
